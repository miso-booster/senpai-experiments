# Sensei-check Metamorphic Rules — Developer Guide

This document explains **how metamorphic testing works in Sensei-check**, the DSL used to specify and verify conversational correctness over *sets of conversations* generated by Sensei-chat. It includes a quick syntax reference, semantics, and ready-to-use examples you can feed to your LLM.

---

## 1) What is a metamorphic rule in Sensei-check?

In Sensei-check, a **rule** states a condition to check over generated conversations. Rules may target:

* a **single** conversation (traditional oracle),
* **several** conversations (this is **metamorphic testing**),
* or **all** conversations (global checks).

Metamorphic rules compare **pairs or tuples of conversations** that meet a selection filter, asserting how outputs should change (or not) when inputs change. This alleviates the oracle problem by checking *relations* rather than absolute answers.

---

## 2) Mental model

1. **Generate conversations** with Sensei-chat (personas, goals, styles). Each conversation is stored with **input selections** (e.g., pizza size) and **extracted outputs** (e.g., price).

2. **Write Sensei-check rules** in YAML. Each rule declares:

   * how many conversations it needs,
   * an optional **filter** (`when`) selecting eligible conversations,
   * and the **relation** to check.

3. Sensei-check evaluates the rules and reports failing cases.

---

## 3) How Sensei-check rules connect to SENSEI Chat profiles

Sensei-check does not live in isolation. In a real project, metamorphic rules almost always check the **outputs of SENSEI Chat profiles**.

* A **SENSEI Chat profile** defines what the simulated user does and which outputs it exposes in `chatbot.output`.
* A **Sensei-check rule** inspects those outputs across one or more conversations using expressions like `conv[i].field_name`.

### 3.1 `conv[i].field` and `chatbot.output`

Whenever you write something like:

```yaml
when: conv[0].size == conv[1].size
if:   len(conv[0].toppings) > len(conv[1].toppings)
then: extract_float(conv[0].price) > extract_float(conv[1].price)
```

you should think of `size`, `toppings`, and `price` as **fields coming from the profile’s `chatbot.output`**.

In a real project:

* The profile’s `chatbot.output` must contain corresponding slots (e.g., `size`, `toppings`, `price`).
* The rule should **not** invent arbitrary fields that the profile does not expose.
* If you rename a field in `chatbot.output`, you must update any rules that refer to it.

The pizza fields used in this guide are **illustrative examples**. When applying Sensei-check in your project:

* Use the actual `chatbot.output` field names from your SENSEI Chat profiles.
* Adapt examples to your domain (e.g., `product_name`, `total_amount`, `pickup_time`, `opening_hours`, etc.).

### 3.2 Three ways rules relate to profiles

There are three common patterns:

1. **Profile-bound rules (most common)**

   * The rule is written for a specific existing profile.
   * All `conv[i].field` references MUST match real `chatbot.output` fields of that profile.

2. **General / global rules**

   * The rule is intentionally profile-agnostic (e.g., language consistency, topic scope, uniqueness, repeated answers).
   * It uses only generic helpers such as `only_talks_about`, `language`, `responds_in_same_language`, `repeated_answers`,
     `data_collected`, `missing_slots`, etc.
   * It does **not** depend on project-specific `chatbot.output` slots.

3. **Rule-first design (less common)**

   * You design a rule before a profile exists.
   * The rule still assumes that a future profile will expose certain outputs.
   * You should clearly document which `chatbot.output` fields a profile must provide for the rule to work.

In most projects you should prefer **profile-bound rules**, and use global rules intentionally and explicitly.

### 3.3 Recommended workflow for profile-bound rules

When creating a new rule that uses profile outputs:

1. **Identify the target profile**

   * Choose the profile whose purpose matches the rule (e.g., “order summary”, “FAQ answer”, “lead qualification”).

2. **Inspect `chatbot.output`**

   * Look at which fields are available, e.g.:

     * `order_id`, `items`, `total_price`, `shipping_address`, …

3. **Design the rule around those fields**

   * Use the same names in `when`, `if`, and `then` expressions:

     * e.g. `conv[0].total_price`, `conv[1].total_price`.

4. **Avoid inventing fields**

   * If you need a new field, update the profile’s `chatbot.output` first, then reference it in the rule.
   * Prefer reusing existing field names across rules to keep things consistent.

5. **Document the relationship**

   * In the rule’s `description`, mention the profile or scenario it targets, e.g.:

     * “Checks monotonicity of `total_price` for the `checkout_summary` profile.”

## 4) Syntax snapshot (metamorphic focus)

```yaml
# Rule header
name: <string>
description: <string>
active: true | false           # optional; inactive rules are ignored
conversations: <N | all>       # N ≥ 2 for metamorphic rules

# Conversation selection
when: <python-expr>            # filter over conv[i].<slot> or scalar slots

# Metamorphic relation
# Option A: simple boolean condition over conv[*]
oracle: <python-expr>

# Option B: if/then relation (clearer for implications)
if:   <python-expr>            # precondition over conv[*]
then: <python-expr>            # expected relation over conv[*]

# Optional helpful message
on-error: <f-string using conv[*] variables>
```

**Accessing conversations.** In metamorphic rules, use the **`conv`** collection:

* `conv[0].size`, `conv[1].drink`, `conv[0].price`, etc.

**Built-in helpers.** You can call functions like `extract_float`, `currency`, `language`, `repeated_answers`, `only_talks_about`, `utterance_index`, `is_unique`, etc., when relevant.

## 5) Canonical examples

### 5.1 Price monotonicity by toppings (2-conversation metamorphic)

> If two orders have the **same size, drink and quantity**, the one with **more toppings** must cost **more**.

```yaml
name: toppings_monotonicity
description: Adding more toppings to a custom pizza costs more (same size/drink/qty)
conversations: 2
when: conv[0].size == conv[1].size and conv[0].drink == conv[1].drink and conv[0].number == conv[1].number
if:   len(conv[0].toppings) > len(conv[1].toppings)
then: extract_float(conv[0].price) > extract_float(conv[1].price)
```

---

### 5.2 Size monotonicity (small ≤ medium ≤ large)

> Holding pizza type and add-ons fixed, **larger sizes** should not be cheaper.

```yaml
name: size_monotonicity
description: small ≤ medium ≤ large (same pizza type & drinks)
conversations: 2
when: conv[0].pizza_type == conv[1].pizza_type and conv[0].drink == conv[1].drink and conv[0].number == conv[1].number
if:   conv[0].size in ['small','medium'] and conv[1].size in ['medium','large']
then: extract_float(conv[0].price) <= extract_float(conv[1].price)
```

---

### 5.3 Language consistency across variations

> If the profile language is English, answers across comparable dialogs should be **in English** (or consistently localized).

```yaml
name: language_consistency
description: Comparable cases respond in the same language (ENG)
conversations: 2
when: conv[0].pizza_type == conv[1].pizza_type and conv[0].size == conv[1].size
oracle: language(conv[0].chatbot_phrases) == 'ENG' and language(conv[1].chatbot_phrases) == 'ENG'
```

Uses the `language` text-analysis helper over chatbot phrases.

---

### 5.4 Robustness to invalid values

> If the user picks an **invalid pizza type**, the assistant must **flag it** somewhere in the dialogue.

```yaml
name: invalid_type_is_rejected
description: Invalid pizza type must be rejected
conversations: 1
if: not all(e in ['margherita','carbonara','marinara','hawaiian','four cheese','vegetarian'] for e in pizza_type)
then: utterance_index('assistant', 'not valid') > 0
```

Illustrates using `utterance_index` to find where rejection occurs.

---

### 5.5 Global uniqueness (all conversations)

> **Order IDs** must be unique across the batch.

```yaml
name: unique_order_ids
description: No duplicate order_id across all conversations
conversations: all
oracle: is_unique('order_id')
```

This mirrors the paper’s uniqueness example (Listing 5).

### 5.6 Profile-bound example: `chatbot.output` + rule

The pizza examples below assume there is a SENSEI Chat profile that exposes the right outputs. For example:

```yaml
# profiles/pizza_order_summary.yaml
name: pizza_order_summary
description: Summarises a pizza order and exposes key fields.
chatbot:
  output:
    - size:
        type: string           # small / medium / large
        description: Pizza size
    - toppings:
        type: list[string]     # list of chosen toppings
        description: Selected toppings
    - drink:
        type: string
        description: Chosen drink
    - number:
        type: int              # quantity
        description: Number of pizzas
    - price:
        type: currency
        description: Final price (e.g. "18.50 EUR")
```

A Sensei-check rule that checks price monotonicity with toppings could be:

```yaml
# rules/toppings_monotonicity.yaml
name: toppings_monotonicity
description: Adding more toppings to a custom pizza costs more (same size/drink/qty)
conversations: 2
when: conv[0].size == conv[1].size and conv[0].drink == conv[1].drink and conv[0].number == conv[1].number
if:   len(conv[0].toppings) > len(conv[1].toppings)
then: extract_float(conv[0].price) > extract_float(conv[1].price)
```

Here:

* Every field (`size`, `toppings`, `drink`, `number`, `price`) comes from the profile’s `chatbot.output`.
* If the profile does not expose `price`, this rule will not work until you add it.
* If you rename a field in the profile (e.g., `total_price` instead of `price`), you must update the rule accordingly.

When applying this pattern to your own project:

* Replace the example profile with your real profile.
* Replace fields (`size`, `toppings`, etc.) with your real `chatbot.output` fields.
* Keep the **structure** of the metamorphic relation, but adapt the **field names** and description.

## 6) Writing good metamorphic rules

### 6.1 Choose *stable* invariants or monotonic relations

Pick relations the system **should** preserve when you:

* change **inputs** in controlled ways (e.g., more toppings → price ↑), or
* keep key inputs **equal** and check conversational **style** (same language, no topic drift).

### 6.2 Filter precisely with `when`

Use `when:` to create **comparable cohorts** (e.g., same size & drinks). This keeps your relations meaningful and reduces false positives.

### 6.3 Prefer `if`/`then` for clarity

`if`/`then` reads like a **law** (“If X changes this way, then Y should change that way”), which is exactly the metamorphic mindset.

### 6.4 Leverage the helper library (authoritative set)

Rules can also check **style** or **semantics** (language, tone, topic boundaries, repetition, slot filling, semantic agreement). Use only the helper functions below; they mirror the exact helpers exported by Sensei-check (`util_functions_to_dict` / `util_to_wrapper_dict`). Names shown are the wrappers available to rules (no leading underscores).

Conversation-level helpers:

| Function                                   | Purpose                                                                           | Example                                                                    |
| ------------------------------------------ |-----------------------------------------------------------------------------------| -------------------------------------------------------------------------- |
| `extract_float(text)`                      | First float/int in a string                                                       | `extract_float(price_text) >= 10`                                          |
| `currency(text)`                           | Currency symbol/abbr/name → ISO code                                              | `currency(price_text) == 'USD'`                                            |
| `language(text_or_list)`                   | Detect language                                                                   | `language(chatbot_phrases) == 'ENG'`                                       |
| `length(item, kind)`                       | Min/max/avg length of strings                                                     | `length(chatbot_phrases,'average') < 2000`                                 |
| `tone(item)`                               | Tone classification (POSITIVE/NEGATIVE/NEUTRAL) per string                        | `'NEGATIVE' not in tone(chatbot_phrases)`                                  |
| `conversation_length(who='both')`          | Number of turns from `user`, `assistant`, or both                                 | `conversation_length('assistant') <= 6`                                   |
| `utterance_index(who, what)`               | Turn index where a role mentions a topic (LLM-backed)                             | `utterance_index('assistant','invalid type') > 0`                          |
| `chatbot_returns(what, and_not=None)`      | Turn indexes where the assistant contains a pattern and not an optional second    | `len(chatbot_returns('LINK: <empty>')) == 0`                               |
| `repeated_answers(method='exact',threshold=0.4)` | Detect near-duplicate assistant replies                                           | `len(repeated_answers('tf-idf',0.75)) == 0`                                |
| `only_talks_about(topics,fallback=None)`   | Topic-scope adherence; returns `True` or out-of-scope responses                   | `only_talks_about('pizza orders, delivery info') is True`                  |
| `responds_in_same_language()`              | Assistant replies in the same language as the user                                | `responds_in_same_language() is True`                                      |
| `semantic_content(value,desc)`             | LLM check for semantic match                                                      | `semantic_content(opening_hours,'1pm-11:30pm daily')`                      |
| `data_collected()`                         | All extracted outputs are non-null                                                | `data_collected() is True`                                                 |
| `missing_slots()`                          | List of slots still `None`                                                        | `missing_slots() == []`                                                    |

Dataset/global helpers:

| Function                      | Purpose                                            | Example                                                           |
| ----------------------------- |---------------------------------------------------- | ----------------------------------------------------------------- |
| `is_unique(property)`         | Property is unique across all conversations        | `is_unique('order_id')`                                           |
| `exists(condition:str)`       | Any conversation satisfies the expression          | `exists(\"conv[0].size=='large' and extract_float(conv[0].price)>0\")` |
| `num_exist(condition:str)`    | Count of conversations satisfying the expression   | `num_exist(\"language(chatbot_phrases)=='ESP'\") >= 5`             |

Similarity options for `repeated_answers`: `tf-idf`, `jaccard`, `sequence-matcher`, or `exact` (default). Some helpers are LLM-backed (`language`, `tone`, `utterance_index`, `only_talks_about`, `responds_in_same_language`, `semantic_content`) so allow for minor variability.

> **Profiles and helpers**  
> Some helpers (like `extract_float`, `currency`, `semantic_content`, `data_collected`, or `missing_slots`) are typically applied
> to fields coming from a profile’s `chatbot.output` (e.g., `conv[0].price`, `conv[0].opening_hours`).  
> Others (like `only_talks_about`, `language`, `responds_in_same_language`, `repeated_answers`) are naturally used in **global rules**
> that do not depend on a specific profile schema.  
> When you design a rule, make it explicit whether it:
>
> * targets a specific profile and its `chatbot.output`, or
> * is a profile-agnostic global rule using only generic helpers.
>

## 7) End-to-end example set (ready to paste)

Below is a suite combining single-conversation oracles, 2-conversation metamorphic rules, and a global rule. Return **one YAML document per fenced block**—emit multiple blocks rather than separating documents with `---`.

```yaml
# Single-conversation: base price sanity for small size
name: small_base_price_floor
description: Small pizzas should cost at least $10
conversations: 1
when: size == 'small'
oracle: extract_float(price) >= 10 and currency(price) == 'USD'
```

```yaml
# Metamorphic: same configuration, more toppings ⇒ higher price
name: toppings_monotonicity
description: More toppings increases total price
conversations: 2
when: conv[0].size == conv[1].size and conv[0].drink == conv[1].drink and conv[0].number == conv[1].number
if:   len(conv[0].toppings) > len(conv[1].toppings)
then: extract_float(conv[0].price) > extract_float(conv[1].price)
```

```yaml
# Metamorphic: size monotonicity
name: size_monotonicity
description: Larger size not cheaper when other factors equal
conversations: 2
when: conv[0].pizza_type == conv[1].pizza_type and conv[0].drink == conv[1].drink and conv[0].number == conv[1].number
if:   (conv[0].size, conv[1].size) in [('small','medium'),('medium','large'),('small','large')]
then: extract_float(conv[0].price) <= extract_float(conv[1].price)
```

```yaml
# Style/Scope: assistant stays on topic
name: scope_guardrails
description: Assistant does not drift from pizza domain
conversations: 1
oracle: only_talks_about('pizza and drink orders, delivery, store info')
```

```yaml
# Global: ID uniqueness
name: unique_order_ids
description: Every conversation has a unique order_id
conversations: all
oracle: is_unique('order_id')
```

## 8) How Sensei-check evaluates rules (under the hood)

* Conversations are recorded with **inputs** (the values the simulator chose) and **outputs** the LLM extracted (e.g., price, order_id).
* For each rule, Sensei-check selects conversations via `when:` and applies the **oracle** or **if/then** relation across the matching tuple(s). Failures are reported with counts and optional error messages; aggregate stats (runs, pass/fail, not-applicable) are exported to CSV/console.

---

## 9) Best practices & pitfalls

* **Design profiles for coverage.** Use systematic generators/selector combinations (e.g., `forward`, nested dependencies) so your metamorphic filters (`when:`) will find enough comparable pairs.
* **Keep filters tight.** Metamorphic relations assume *ceteris paribus* conditions—control confounders in `when:`.
* **Prefer numeric comparisons on parsed values.** Use `extract_float(price)` instead of substring checks.
* **Use style checks to catch UX regressions.** `language`, `repeated_answers`, `only_talks_about` are effective for LLM-based bots where answers vary.
* **Expect some LLM variability.** For style/semantic functions (LLM-powered), calibrate thresholds (e.g., `repeated_answers` similarity).

## 10) Adapting to other domains (quick sketches)

* **Travel:** “Same route/day; *higher class* ⇒ *fare not lower*.”
  Filter by origin/destination/date; compare `fare` fields.

* **Banking:** “Same amount/beneficiary; *higher fee tier* ⇒ *total debit ≥*.”
  Compare `total_debit` as fee tier varies.

* **Customer support SLAs:** “Same issue; *priority up* ⇒ *promised response time ≤*.”

These follow the same pattern as the pizza examples: hold confounders equal, vary one dimension, assert monotonicity or invariance.
