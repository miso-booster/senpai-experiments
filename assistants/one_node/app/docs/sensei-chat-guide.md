# Sensei Profiles: How It Works and How to Author a Profile

> This guide focuses on **profiles**—the YAML files that define how Sensei’s user simulator behaves—and provides just enough context about how Sensei runs so you can create, validate, and execute profiles confidently.

---

## 1) What Sensei Is (in one minute)

Sensei is a **user simulator** for chatbot testing. You give it a profile (a YAML file) that describes the simulated user’s language, role, context, goals, data types, interaction style, and so on. Sensei then talks to your target chatbot, logs the conversation, and can extract structured outputs for validation.

- **Profiles are YAML** and live under a project’s `profiles/` directory.
- **Custom data types** go in `types/`.
- **Optional personalities** (prompt fragments) go in `personalities/`.
- You can execute Sensei by passing CLI arguments **or** by using a `run.yml` inside your project.

---

## 2) Project Layout (where profiles live)

When you run the project initializer, Sensei creates a folder with these key locations:

```
project_folder/
  personalities/     # optional prompt snippets for user “personas”
  profiles/          # your user profile YAMLs (or a folder of profiles)
  rules/             # rules and metamorpfic rules for testing
  types/             # custom data-type YAMLs (regex + extraction schema)
  run.yml            # optional: run configuration so you don’t type long CLIs
```

Only `profiles/` (and optionally `types/` and `personalities/`) matter for authoring profiles. The rest is convenience or for advanced testing.

## 2.1) How profiles interact with Sensei-check rules

Sensei-check uses the conversations generated by Sensei Profiles to run **metamorphic rules**. In that pipeline:

- Profiles generate conversations and define what should be extracted in `chatbot.output`.
- Sensei-check rules then read those extracted outputs via expressions like `conv[i].field_name`.

### 2.1.1 `chatbot.output` as the contract for rules

The `chatbot.output` section defines a **schema** of fields that:

- the extractor will populate at the end of each conversation, and
- Sensei-check rules will refer to as `conv[i].<field_name>`.

Example:

```yaml
chatbot:
  output:
    - total_price:
        type: currency
        description: "Final price including taxes and add-ons"
    - booking_id:
        type: string
        description: "Booking reference"
```

In rules, you might then write:

```yaml
when: conv[0].booking_id is not None
then: extract_float(conv[0].total_price) > 0
```

Here, `total_price` and `booking_id` come directly from `chatbot.output`.

### 2.1.2 Designing `chatbot.output` with rules in mind

When you design a profile, think about:

- Which **business properties** or **behavioural invariants** you want to test with rules later (e.g., monotonicity of price, field completeness, uniqueness, topic scope).
- Which fields the rules will need to access.

Best practices:

- Use stable, descriptive names (e.g., `total_price`, `opening_hours`, `order_id`) instead of names tied to one particular experiment.
- Avoid duplicating the same concept under many different names across profiles; reuse names when semantics are the same.
- If you know you will write rules about a field, make sure it appears in `chatbot.output` and has the right `type` (e.g., `currency` instead of a raw `string`).

### 2.1.3 Profile-bound vs global rules

From the profile’s viewpoint, you will typically see two kinds of rules:

1. **Profile-bound rules**

   - Target a specific profile (e.g., `pizza_order_summary`).
   - Rely on its `chatbot.output` fields (e.g., `size`, `toppings`, `price`).
   - The rule should be updated if you rename or remove these fields.

2. **Global rules**

   - Apply to many profiles or the whole dataset.
   - Use generic helpers such as `only_talks_about`, `language`, `responds_in_same_language`, `repeated_answers`, `data_collected`, etc.
   - Do not require a particular `chatbot.output` schema to make sense.

When you create or change a profile, ask:

- “Which profile-bound rules might be affected if I rename/remove this field?”
- “Do I need to add a new field so that rules can express the checks I care about?”

Keeping this contract in mind will make your rules and profiles evolve together without surprises.

## 3) Profile File: high‑level anatomy

A profile is a single YAML file (or a **folder** with multiple YAMLs for batch execution). These are the top-level sections you’ll use most:

```yaml
test_name: "string"

llm:
  temperature: float
  model: "provider-specific name"
  model_prov: "langchain provider key"
  format:
    type: text | speech
    # config: path/to/speech_config.yml   # (only for type: speech)

user:
  language: English | Spanish | ...
  role: "prompt describing the simulated user"
  context:
    - personality: personalities/<file>.yml   # optional
    - "freeform constraints, facts, preferences …"
  goals:
    - "freeform goal with {{variables}}"
    - variable_name:
        function: default|random|forward|another|pairwise(...)
        type: string|int|float|<custom>
        data: ... # list, range, generator, or LLM-generated list

chatbot:
  is_starter: true|false
  fallback: "bot’s real fallback message"
  output:
    - field_name:
        type: <primitive|list[primitive]|custom>
        description: "what to extract at the end"

conversation:
  number: <int> | combinations | combinations(0.6) | combinations(0.6, pairwise)
  max_cost: <float $>      # optional: cap spend for the whole run
  goal_style:              # how/when a conversation ends
    steps: <int> | random steps: <max> | all_answered:
      export: true|false   # export the verification dataframe
      limit: <int>         # safety stop; default 30 if omitted
    max_cost: <float $>    # optional: per‑conversation cost cap
  interaction_style: # choose one or many from here
    - long phrases | change your mind | change language: [italian, portuguese, ...] | make spelling mistakes | single questions | all questions
    - random: [any of the above] # there can be some interaction styles fixed and then some random, check the docs of the interaction_style section
```

> Tip: Each **goal** can be a plain string (with optional `{{variables}}`) or a mapping that **declares** that variable’s `type`, `data`, and fill-in `function`.

## 4) Writing `user.goals`: variables, data, and functions

### 4.1 Variables in text

Write prompts like:
`- "Order a {{size}} pizza with {{toppings}} and {{cans}} cans of {{drink}}"`

Each `{{variable}}` must be declared elsewhere in the `goals` list with **exactly the same name** (case‑sensitive).

### 4.2 Types (default vs custom)

**Default types:**
- `int`: data as an integer.
- `float`: data as a float.
- `string`: data as text.

**Custom types:** define a YAML file in `types/` that gives:

- a `name` (must match the file name without extension),
- a `type_description` (prompt that explains the type),
- a `format` (Python regex for matching),
- an `extraction` schema describing how to parse the match into one or more typed values.


> No `list` type is used in `user.goals `.


**Examples**

`types/phone_number.yml`:

```yaml
name: phone_number
type_description: A phone number
format: r"^\d{3}-\d{7}$"
extraction: str
```

`types/currency.yml`:

```yaml
name: currency
type_description: A float number with a currency
format: r'\d+(?:[.,]\d+)?\s*(?:[\$\€\£]|USD|EUR)'
extraction:
  value:
    type: float
    description: a float value
  currency:
    type: string
    description: a currency unit
```

### 4.3 Data sources for variables

You can populate the `data` for a variable in several ways:

- **Explicit list** (strings or numbers).
- **Numeric range** for `int`/`float` using `min`, `max`, `step` (or `linspace` for floats).
- **LLM-generated list** with `any("<instruction>")`, optionally mixing with manual items.
  Example:

  ```yaml
  data:
    - "Fanta"
    - any(3 soda drinks)
    - any(alcoholic drinks)
  ```

- **Custom list function** (your own Python generator):

  ```yaml
  data:
    file: list_functions/number_list.py
    function_name: shuffle_list      # or your custom function
    args: [1, 6, 2]    # can be completed with a yaml containing a list (args: list_functions/list_of_things.yml)
  ```

### 4.4 Fill functions (how values are chosen each run)

- `default()` → use **all** items.
- `random()` → pick **one** at random.
- `random(5)` → pick **N** random items (N ≤ list length).
- `random(rand)` → pick a **random count** of random items.
- `another()` → cycle randomly through options without repetition until exhausted.
- `another(5)` → pick N unique items each time; no repetition across conversations until options are used.
- `forward()` → iterate deterministically through items, enabling **nesting** to cover combinations (e.g., `forward(drink)` depends on `drink`).
- `pairwise()` → generate pairwise‑coverage combinations across **2+ variables** (greatly reduces total cases while still catching most 2‑way defects). A minimum of 2 pairwise assigned variables are needed to use it.

> Nest `forward()` to produce a grid of combinations; use `pairwise()` on two‑plus variables to cover **every pair at least once** without full Cartesian explosion.

## 5) Conversation controls that matter for profiles

Although not strictly part of “user definition,” these fields strongly affect how a profile will execute and end:

### `conversation.number`

- A fixed integer, or
- `combinations` → use the **largest** combinations matrix produced by `forward`/`pairwise`, or
- `combinations(p)` → use a fraction (e.g., `0.6` = 60%), optionally restricted to a function: `combinations(1, forward)`.

> Important: a minimum of two nested forward or two pairwise functions are needed to be declared in the variables in the 'goals' field to define a 
> conversation number from a combination matrix.

### `goal_style`

Choose one of:

- Fixed `steps: N`.
- `random steps: M` (random 1..M, M ≤ 20).
- `all_answered:` with optional `export: true` and `limit: 20` (safety cap; default 30). When `export: true`, a .csv dataframe is generated containing which outputs have been satisfied.

You can also set `goal_style.max_cost` to cap **per‑conversation** spend; `conversation.max_cost` caps the **entire run**.

### `interaction_style`

These styles alter how the user will talk, you can choose one or many.
Interaction styles are not natural language prompts, they are a set of reserved keywords that you can choose from, so never translate them or choose one that is not below.

- `long phrases`: the user will use very long phrases to write any query.
- `change your mind`: the user will change their mind eventually. Useful in conversations when the user has to provide information, such as toppings on a pizza, an appointment date...
- `change language`: the user will change the language in the middle of a conversation. This should be defined as a list of languages inside the parameter, as shown in the example above.
  - Here make a list with the languages like: "Spanish", "German", etc.
- `make spelling mistakes`: the user will make typos and spelling mistakes during the conversation.
- `single questions`: the user makes only one query per interaction from "goals" field.
- `all questions`: the user asks everything inside the "goals" field in one interaction.
- `default`: the user simulator will carry out the conversation in a natural way.

There is also the possibility of using `"random: [<interaction_styles>]"`. This option allows creating a list inside with any of the interaction styles mentioned. Then, it selects a random amount of interaction styles to apply to the conversation.

Example:

```yaml
interaction_style:
- long phrases
- random:
    - make spelling mistakes
    - change language:
      - italian
      - portuguese
      - chinese
```

## 6) Chatbot output extraction (schema at the end of a run)

Define what you want extracted after the conversation, for validation or reporting **and for Sensei-check rules to inspect**. Each field you define here can later be read in rules as `conv[i].<field_name>`. Example:

```yaml
chatbot:
  output:
    - price:
        type: currency
        description: "final price for the order"
    - time_to_ready:
        type: time("hh:mm:ss")     # accepts natural-language format specifiers
        description: "prep ETA"
    - order_id:
        type: string
        description: "the order identifier"
```

Default types accepted in `output` include the primitives (`int`, `float`, `string`) plus `time(...)`, `date(...)`, and lists like `list[int]` or `list[string]`. Custom types work here as well.

- int: Outputs data as an integer.
- float: Outputs data as a float.
- string: Outputs data as text.
- time/time("format"): Outputs data in a time format. An output format can be specified by adding a parenthesis with the desired format written in natural language. Ex: time(UTC), time(hh:mm:ss), time(show time in hours, minutes, and seconds).
- date/date("format"): Outputs data in a date format. Following the same logic as "time" type, a date format can be specified in natural language. Ex: date(mm/dd/yyyy), date(day-month-year), date(show date in days, months, and years).
- list[type]: Outputs a list of the specified data inside the brackets.



> Note that custom types can be used in both `user.goals` and `chatbot.output` because they are defined in YAML files with the following structure.
> 
> Example:
> ```
> name: phone_number
> type_description: A phone number
> format: r"^\d{3}-\d{7}$"
> extraction: str
>```
>Only the `format` field is used in `user.goals`, whereas the `extraction` field is used in `chatbot.output`.
> 
> This design allows custom types to be compatible with both fields. However, this does not imply that default types can be used interchangeably. For example, default types such as `list`, `time`, or `date` may be valid in `chatbot.output` but can raise an exception if used in `user.goals`.

## 7) Full example profile (end‑to‑end)

Below is a **complete, runnable** profile that demonstrates variables, custom types, functions, and execution controls without copying the pizza example.

```yaml
test_name: "rental_car_quote_smoke"

llm:
  temperature: 0.7
  model: gpt-4o
  model_prov: openai
  format:
    type: text

user:
  language: English
  role: >
    You are a customer trying to book a rental car for a weekend trip.
    Ask for availability, pricing, insurance options, and pickup/return details.
  context:
    - personality: personalities/calm-user.yml
    - "You prefer automatic transmission."
    - "You are a member of a loyalty program."
  goals:
    - "Book a {{car_class}} car with {{transmission}} and {{seats}} seats"
    - "Pickup on {{pickup_date}} and return on {{return_date}}"
    - "Add-ons: {{add_ons}}"
    - "Ask for a total price in {{currency}}"
    - car_class:
        function: forward()
        type: string
        data: [economy, compact, suv]
    - transmission:
        function: pairwise()
        type: string
        data: [automatic, manual]
    - seats:
        function: forward(car_class)
        type: int
        data:
          min: 2
          max: 7
          step: 1
    - pickup_date:
        function: another()
        type: string
        data:
          - any(3 dates within the next 30 days)
    - return_date:
        function: forward(pickup_date)
        type: string
        data:
          - any(3 dates)
    - add_ons:
        function: pairwise()
        type: string
        data: [GPS, infant seat, additional driver, insurance]
    - currency:
        function: random()
        type: string
        data: [USD, EUR, GBP]

chatbot:
  is_starter: false
  fallback: "Sorry, could you rephrase that?"
  output:
    - total_price:
        type: currency
        description: "Final price including taxes and add-ons"
    - pickup_time:
        type: time("hh:mm")
        description: "Pickup time"
    - booking_id:
        type: string
        description: "Confirmation / booking reference"

conversation:
  number: combinations(0.5, pairwise) # two pairwise functions have been declared
  goal_style:
    steps: 6
    max_cost: 0.1
  interaction_style:
    - random:
      - make spelling mistakes
      - single questions
      - long phrases
      - change language:
        - Spanish
        - German
```

## 8) Authoring workflow (minimal steps)

1. **Initialize** a project (once):

   ```bash
   python init_project.py --path /abs/path/to/project --name my-bot-tests
   ```

2. **Create your profile** under `profiles/` (use the example as a template).
   If you need custom types, add them under `types/` (see §4.2).
   Optional: create `personalities/` YAMLs for reusable persona prompts.

3. **Run Sensei** with CLI flags **or** via `run.yml`:

   **CLI example**

   ```bash
   python sensei_chat.py      --technology taskyto      --connector-params "base_url=http://localhost,port=5000"      --project-path /abs/path/to/project      --user-profile profiles/rental_car_quote_smoke.yml      --output /abs/path/to/output      --verbose
   ```

   **run.yml example**

   ```yaml
   project_folder: /abs/path/to/project
   user_profile: profiles/rental_car_quote_smoke.yml   # or a folder of profiles
   technology: taskyto
   connector_params:
     base_url: http://localhost
     port: 5000
   output: /abs/path/to/output
   execution_parameters:
     - verbose
   ```

   Then run:

   ```bash
   python sensei_chat.py --run-from-yaml /abs/path/to/project
   ```

4. **Validate** your profile before or after a run:

   ```bash
   python validation_check.py      --profile /abs/path/to/project/profiles/rental_car_quote_smoke.yml      --output  /abs/path/to/output      --combined-matrix      --verbose
   ```

This produces a JSON with any format errors and CSVs with the value‑combination matrices (great for inspecting `forward`/`pairwise` coverage).

## 9) Best practices & pitfalls

- **Keep variable names stable**—they must **exactly** match the `{{…}}` usage in goal strings.
- Variables declared in `user.goals` should be used in goal prompts.
- Prefer **`pairwise()`** to cover many options efficiently; use **nested `forward()`** when full grids are intentional.
- With `random(n)`, ensure **`n ≤ list length`**. With `another(n)`, you won’t get repeats until the pool is exhausted.
- If you test multilingual bots, try `interaction_style: change language: [...]` and set `user.language` to your default.
- For time/cost safety, set **`conversation.max_cost`** and/or **`goal_style.max_cost`**.
- Put **real bot fallback text** in `chatbot.fallback` to avoid endless loops.
- For ASR tests, switch `llm.format.type` to `speech` and point `config` to your speech settings.
- Keep custom `types/` regexes tight and accompany them with a clear `extraction` schema.
- Store commonly reused prompts as YAMLs under `personalities/` and reference them via `context`.
- When a range of values is needed, prefer using "min max step" (or linspace for float) listing rather than listing range separated values.

## 10) Quick reference: functions

| Function        | What it does                                                 |
|-----------------|--------------------------------------------------------------|
| `default()`     | Use all `data` values.                                       |
| `random()`      | Pick one at random.                                          |
| `random(n)`     | Pick **n** random values (no more than list length).         |
| `random(rand)`  | Pick a random count of random values.                        |
| `another()`     | No repeats until options are exhausted.                      |
| `another(n)`    | Pick **n** unique values per conversation, cycling overall.  |
| `forward()`     | Deterministic iteration; supports **nesting by dependency**. |
| `pairwise()`    | Cover all pairwise combinations across 2+ variables.         |

## 11) FAQ

**Q. Do I have to define `llm`?**
No. If omitted, defaults are applied (e.g., model and temperature) and the format defaults to text. Add it when you need overrides or `speech` mode.

**Q. Where do I put custom types?**
In your project’s `types/` folder as separate YAMLs. Reference by name in `goals` or `chatbot.output`.

**Q. Can I run a whole folder of profiles?**
Yes—set `--user-profile` to a folder or put that folder path into `run.yml:user_profile`.
