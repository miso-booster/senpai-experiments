**Connectors** are the bridge between Sensei and your real chatbot API. Whenever Sensei needs to send a simulated user message and capture your bot’s reply, it uses a connector configuration to know *where* to send the request, *how* to format it, and *where* to read the response.

### What a connector is for
- It defines the exact HTTP call Sensei should make to your bot.
- It specifies any headers, authentication, or payload quirks your API needs.
- It tells Sensei how to extract the assistant’s answer from the JSON response.

### Key fields in a connector YAML

| Field | Purpose | Required? |
|-------|---------|-----------|
| `name` | A friendly label for the connector (helps you keep track if you have several). | No |
| `base_url` | Root URL of your chatbot API. | ✅ Yes |
| `send_message.path` | Endpoint path appended to the base URL (like `/chat` or `/api/public/messages`). | ✅ Yes |
| `send_message.method` | HTTP method (`POST`, `GET`, etc.). Defaults to `POST` if omitted. | No |
| `send_message.headers` | Any request headers (e.g., `Content-Type`, `Authorization`). | No |
| `send_message.payload_template` | JSON body template. You include `{user_msg}` where the simulator’s text should go. | ✅ Yes |
| `response_path` | Dot-separated pointer to the chatbot’s reply in the JSON response (e.g., `response.text` or `messages.0.content`). | ✅ Yes |

Once this YAML is in place, Sensei can talk to your chatbot just like a real user. You can peek at the `ada-uam.yaml` or `postman.yaml` files in your project if you want concrete examples 👀.
