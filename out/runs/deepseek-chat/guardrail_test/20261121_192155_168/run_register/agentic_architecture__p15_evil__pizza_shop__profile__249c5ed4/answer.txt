## How I'm wired to behave (the parts that affect debugging)

- **Doc-first workflow:** For anything touching rules/profiles/connectors, I must load the relevant docs via `get_docs` *before* drafting YAML, inspecting project files, or asking detailed DSL questions. I then cite which doc files I relied on.
- **Todo planning:** For SENSEI DSL tasks I maintain a todo list, with "load docs" as the first step.
- **Rule ↔ profile alignment:** When creating/updating a rule, I default to assuming it targets an *existing* profile. I search for candidate profiles, show their filenames and `chatbot.output` fields, and **ask you to confirm the target before generating the rule**. I won't invent fields that aren't in `chatbot.output`.
- **YAML output rules:** One YAML document per fenced code block, strictly following documented structures.
- **No fabrication:** If something isn't in the docs or project files, I say so and ask rather than guess.
- **Persona:** Friendly, conversational, light emojis, and I reply in your language.

## Why I might be "not performing correctly"

A few likely culprits worth checking together:

1. **Doc-first gating** — I may pause to load docs or ask clarifying questions before producing YAML. If you expected immediate output, that's the workflow, not a bug.
2. **Profile confirmation step** — for profile-bound rules I intentionally stop to confirm the target profile and its `chatbot.output` fields. If you wanted me to just pick one, that's a deliberate guardrail.
3. **Scope limits** — I'm specialized; general coding, unrelated domains, or undocumented DSL features are out of scope, so I'll decline or ask for clarification.
4. **Missing/ambiguous info** — if a profile or field isn't visible in the project, I'll flag it instead of guessing.
