## 🧱 What "valid profile" actually means (the contract your automation must satisfy)

From `sensei-chat-guide.md`, a profile is a single YAML with these top-level sections:

| Section | Required? | Key constraints |
|---|---|---|
| `test_name` | ✅ | string |
| `llm` | optional | `temperature`, `model`, `model_prov`, `format.type: text\|speech` |
| `user.language` | ✅ | e.g. `English` |
| `user.role` | ✅ | prompt describing the simulated user |
| `user.context` | optional | list of strings or `personality: personalities/<file>.yml` |
| `user.goals` | ✅ | list of goal strings + **variable declarations** |
| `chatbot.is_starter` | ✅ | bool |
| `chatbot.fallback` | ✅ | the bot's **real** fallback text |
| `chatbot.output` | ✅ | list of `field_name: {type, description}` |
| `conversation.number` | ✅ | int, `combinations`, `combinations(p)`, `combinations(p, fn)` |
| `conversation.goal_style` | ✅ | `steps: N` \| `random steps: M` \| `all_answered: {export, limit}` |
| `conversation.interaction_style` | optional | reserved keywords only |

## ⚠️ The 5 validation traps an LLM generator most often falls into

These are the things your automation **must enforce** (they're the most common reasons a generated profile fails `validation_check.py`):

1. **Variable name matching** — every `{{var}}` in a goal string must have a declaration with the *exact same, case-sensitive* name in `user.goals`.
2. **No unused variables** — declared variables should actually appear in a goal prompt.
3. **Type legality per section** — `list`, `time`, `date` are valid in `chatbot.output` but **raise exceptions in `user.goals`**. Only `int`, `float`, `string`, or custom types in goals.
4. **Function/data consistency**:
   - `random(n)` / `another(n)` → `n ≤ len(data)`
   - `pairwise()` → needs **≥ 2** pairwise variables
   - `combinations` as `conversation.number` → needs **≥ 2** nested `forward()` or `pairwise()` variables
5. **`interaction_style` keywords are reserved** — never translate them, never invent new ones. Valid set: `long phrases`, `change your mind`, `change language: [...]`, `make spelling mistakes`, `single questions`, `all questions`, `default`, `random: [...]`.

## 🐍 Suggested automation architecture (LLM-driven, doc-grounded)

Since I can't write the script, here's the blueprint you can hand to your coding LLM:

```
1. PROMPT STAGE
   - Feed the LLM the sensei-chat-guide.md schema + a real example profile
     (e.g. your pizza_and_drink_order_placement.yaml) as few-shot.
   - Ask for JSON output first (structured), then render to YAML.
     → JSON is easier to validate programmatically than raw YAML.

2. SCHEMA VALIDATION STAGE (deterministic, no LLM)
   - Pydantic / jsonschema model mirroring the table above.
   - Enforce the 5 traps listed above as custom validators.

3. SEMANTIC VALIDATION STAGE
   - Cross-check {{vars}} ↔ declarations (regex extract from goal strings).
   - Check function/data cardinality rules.
   - Check interaction_style against the reserved keyword whitelist.

4. REPAIR LOOP
   - If validation fails, feed the error messages back to the LLM
     and ask for a corrected JSON. Cap at 2–3 retries.

5. FINAL CHECK
   - Write YAML to profiles/, then run the official
     `python validation_check.py --profile <path> --combined-matrix --verbose`
     as the ground-truth gate.
```

## 📋 A minimal valid template to anchor your generator

This is the "ready-made template" from the docs, which is the safest starting point for few-shot prompting:

```yaml
test_name: "my_first_sensei_profile"

llm:
  temperature: 0.8
  model: gpt-4o
  model_prov: openai
  format:
    type: text

user:
  language: English
  role: "Describe what the simulated user wants and how they behave."
  context:
    - "Who the user is, constraints, preferences, availability, etc."
  goals:
    - "Main request with a {{variable}}"
    - variable:
        function: random()
        type: string
        data: [option1, option2, option3]

chatbot:
  is_starter: false
  fallback: "Paste your bot's real fallback here"
  output:
    - important_field:
        type: string
        description: "What you want to extract/validate"

conversation:
  number: 2
  goal_style:
    steps: 5
  interaction_style:
    - random:
      - long phrases
      - make spelling mistakes
```

## 💡 One design tip from your own project

Looking at `pizza_and_drink_order_placement.yaml`, notice how `chatbot.output` uses `type: money` and `type: time` — those are **custom types** that must exist in your `types/` folder. So your automation should also:

- **Detect custom types** referenced in `chatbot.output` and verify the corresponding `types/<name>.yml` exists (with `name`, `type_description`, `format`, `extraction`).
- If a custom type is missing, either generate it or fall back to a primitive.
