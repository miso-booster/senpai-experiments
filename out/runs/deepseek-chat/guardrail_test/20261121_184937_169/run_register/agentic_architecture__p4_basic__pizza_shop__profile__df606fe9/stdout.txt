## What your automation must generate (the "valid profile" contract)

Based on `sensei-chat-guide.md`, a valid profile is a single YAML doc with these top-level sections:

- **`test_name`** — string.
- **`llm`** *(optional)* — `temperature`, `model`, `model_prov`, `format.type: text|speech`.
- **`user`** — `language`, `role`, `context` (list, optional `personality:` refs), and `goals`.
  - `goals` mixes **plain goal strings** (with `{{variables}}`) and **variable declarations** (`function`, `type`, `data`).
  - Every `{{var}}` must have a matching declaration (case-sensitive).
  - `function` ∈ `default() | random() | random(n) | random(rand) | another() | another(n) | forward() | forward(dep) | pairwise()`.
  - `type` ∈ `int | float | string | <custom type name>` (no `list`/`time`/`date` here!).
  - `data` = explicit list, `{min,max,step}` / `linspace`, `any("...")` LLM-generated items, or a custom list function file.
- **`chatbot`** — `is_starter`, `fallback`, and `output` (the schema rules read as `conv[i].<field>`).
  - `output` types: `int | float | string | time(...) | date(...) | list[...] | <custom>`.
- **`conversation`** — `number` (int or `combinations(...)`), `max_cost`, `goal_style` (`steps` / `random steps` / `all_answered`), `interaction_style` (reserved keywords only).

## Key validation gotchas your LLM generator should enforce ✅

1. Every `{{var}}` in goal strings has a matching declaration.
2. `random(n)` / `another(n)` → `n ≤ len(data)`.
3. `combinations(...)` requires ≥2 `forward`/`pairwise` variables.
4. `pairwise()` needs ≥2 pairwise-assigned variables.
5. `interaction_style` uses **exact reserved keywords** (never translated/invented).
6. `user.goals` types ≠ `chatbot.output` types (don't put `list`/`time`/`date` in goals).
7. `chatbot.fallback` should be the bot's **real** fallback text.
