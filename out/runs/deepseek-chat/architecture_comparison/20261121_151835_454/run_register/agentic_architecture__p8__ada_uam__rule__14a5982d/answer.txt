## Short answer: it's *almost* okay, but there's one real problem

The fields you reference (`contact_email`, `contact_phone`, `physical_address`) **do exist** in the profile's `chatbot.output` — so the alignment is correct. ✅

But there's a **logic bug**: your `when` clause is identical to your `oracle`. That means the rule only ever runs on conversations where the answer is *already correct*, so it can never fail. It's effectively a no-op (always "not applicable" or trivially true). That defeats the purpose of the check.

## What's wrong, in detail

1. **`when` == `oracle` (the main issue).**
   - `when` is a **filter** that selects which conversations the rule applies to.
   - `oracle` is the **condition** that must hold.
   - If you filter on "the values are correct" and then assert "the values are correct", you're only checking the cases that already pass. The rule can never catch a wrong answer. 🚫

2. **`conversations: 1` is fine** for a single-conversation oracle — no problem there.

3. **No `active` field** — optional, defaults are fine, but I'll add `active: true` for clarity.

4. **No `yields`/`on-error` message** — optional, but a helpful failure message makes debugging much nicer.

## Fixed version

The fix is to **remove the `when` filter** (or make it a meaningful, non-tautological filter). Since this is a simple single-conversation oracle checking fixed CAU contact data, the cleanest approach is to drop `when` entirely and just assert the oracle:

```yaml
name: check_cau_information
description: Checks that the CAU provided correct information about contact details (profile consultante_de_servicios_y_asistencia_del_cau).
conversations: 1
active: true
oracle: conv[0].contact_email == 'cau@uam.es' and conv[0].contact_phone == '91 497 4029' and conv[0].physical_address == 'C/ Francisco Tomás y Valiente nº 11, Building B, first floor, office TI-107'
yields: |
  f"Wrong CAU contact info: email={conv[0].contact_email}, phone={conv[0].contact_phone}, address={conv[0].physical_address}"
```

### What changed and why
- **Removed `when`** — it was a tautology with `oracle`. Now the rule runs on every conversation and actually validates the data.
- **Added `active: true`** — explicit, so it's clearly enabled.
- **Added `yields`** — a helpful message showing the actual extracted values when the check fails.
- **Kept the exact field names** — `contact_email`, `contact_phone`, `physical_address` all match the profile's `chatbot.output`. ✅

## One thing to double-check ⚠️

The exact strings must match **character-for-character** what the bot extracts. In particular:
- The phone `'91 497 4029'` — spacing matters.
- The address `'C/ Francisco Tomás y Valiente nº 11, Building B, first floor, office TI-107'` — accents, `º`, commas, and capitalization all matter.

If the bot might format these slightly differently (e.g., `+34 91 497 4029`, or `nº 11` vs `n.º 11`), the rule will fail on formatting rather than on substance. If you expect formatting variation, consider a more tolerant check (e.g., `semantic_content(conv[0].physical_address, '...')` or `extract_float` on the phone). Want me to make a more robust version? 😊
