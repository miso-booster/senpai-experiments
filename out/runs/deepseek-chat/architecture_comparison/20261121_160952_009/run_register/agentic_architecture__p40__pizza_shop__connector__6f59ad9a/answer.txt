Here's your connector 🎉 — it's a MillionBot-style API, so it maps almost 1:1 to the documented example in `custom-connector-guide.md` / `connector-examples.md`.

```yaml
name: "SAIC Málaga"
base_url: "https://api.1millionbot.com"
send_message:
  path: "/api/public/messages"
  method: "POST"
  headers:
    Content-Type: "application/json"
    Authorization: "64e5d1af081211d24e2cfecd"
    Origin: "https://saic.malaga.eu"
    Referer: "https://saic.malaga.eu/"
    User-Agent: "Mozilla/5.0 (Windows NT 10.0; Win64; x64; rv:147.0) Gecko/20100101 Firefox/147.0"
  payload_template:
    conversation: "6977595c744ccf01954b8797"
    sender_type: "User"
    sender: "6977595c3e4824018e496b0c"
    bot: "64e5d1af081211d24e2cfec8"
    language: "es"
    url: "https://saic.malaga.eu/"
    message:
      text: "{user_msg}"
response_path: "response.0.text"
```

**How it maps to the docs** (`custom-connector-guide.md`, `connector-examples.md`):

- `base_url` → `https://api.1millionbot.com` (host from the request line).
- `send_message.path` → `/api/public/messages`, `method: POST`.
- `headers` → kept the meaningful ones: `Content-Type`, `Authorization` (the raw token, no `Bearer` prefix, matching the MillionBot example), plus `Origin`/`Referer`/`User-Agent` since this API is called cross-site from `saic.malaga.eu` and may check them. Browser-only headers (`Accept-Encoding`, `Sec-Fetch-*`, `Priority`, `Content-Length`, `Host`, `Connection`, etc.) are dropped — the HTTP client sets those itself.
- `payload_template` → the exact JSON body, with `message.text` set to the `{user_msg}` placeholder. The session identifiers (`conversation`, `sender`, `bot`) are hardcoded from your capture, as in the documented example.
- `response_path` → `response.0.text`, because the reply lives in the first element of the `response` array: `{"response":[{"text":"<p>¡Buenos días!...</p>"}]}`.

⚠️ Two things worth knowing:

1. **HTML in the reply** — the bot returns `<p>¡Buenos días!<br><br>¿En qué puedo ayudarte?</p>`. The connector extracts it raw, so your rules will see the HTML tags. If that bothers your validation, either strip tags in the rule logic or keep it in mind when writing oracles.
2. **Session IDs are static** — `conversation` and `sender` are fixed values from your capture. That's fine for testing (same as the docs' example), but if the API rejects reused conversations, you'd need a fresh capture or a dynamic-session connector.
