¡Hola! 😊 Let's take a look at your rule together — I spotted a couple of things worth fixing.

## What's going on

Your rule has a **logical redundancy**: the `when:` filter and the `oracle:` are *identical*. That means the rule only ever evaluates conversations where the data is already correct — so it can never fail. It's essentially checking "if the answer is right, is the answer right?" 🤔

Also, there's a **field mismatch** with your project. Looking at your profiles, the CAU contact fields live in different profiles with different names:

- `consultante_de_servicios_y_asistencia_del_cau.yaml` → `contact_email`, `contact_phone`, `physical_address` ✅
- `asistencia_técnica_y_cuentas.yaml` → `contact_info`, `operational_hours`
- `soporte_técnico_y_gestión_de_contraseñas.yaml` → `contact_email`, `contact_phone`, `contact_address`

So `contact_email` / `contact_phone` / `physical_address` **do exist** — but only in the `consultante_de_servicios_y_asistencia_del_cau` profile. Good to know! 👍

## The fix

The `when:` should be a **light filter** (e.g., "only run when the bot actually provided contact info"), and the `oracle:` should do the real checking. Here's the corrected version:

```yaml
name: check_cau_information
description: Checks that the CAU profile provides the correct contact details (email, phone, address).
conversations: 1
when: conv[0].contact_email is not None
oracle: |
  conv[0].contact_email == 'cau@uam.es'
  and conv[0].contact_phone == '91 497 4029'
  and conv[0].physical_address == 'C/ Francisco Tomás y Valiente nº 11, Building B, first floor, office TI-107'
yields: |
  f"Wrong CAU contact info: email={conv[0].contact_email}, phone={conv[0].contact_phone}, address={conv[0].physical_address}"
```

## Why this is better 🎯

1. **`when:` is now a real filter, not a tautology.** It only skips conversations where the bot never gave an email at all (nothing to check). Every conversation that *did* provide contact info gets validated.

2. **The `oracle:` does the actual work.** This is where the correctness check lives — if any of the three fields is wrong, the rule fails. That's the whole point of a rule! ✅

3. **Added a `yields:` message.** When it fails, you'll see *which* values were wrong instead of just a bare boolean. Super helpful for debugging 👀.

4. **`description:` mentions the target profile.** Per the docs, it's good practice to say which profile the rule is bound to — here it's `consultante_de_servicios_y_asistencia_del_cau`.

## One small heads-up ⚠️

Since this rule is **profile-bound**, make sure you run it against conversations generated by the `consultante_de_servicios_y_asistencia_del_cau` profile — otherwise `contact_email` etc. won't exist and the rule will error out. If you want it to be more forgiving across profiles, you could add a guard like:

```yaml
when: conv[0].contact_email is not None and conv[0].contact_phone is not None
```

That way it silently skips conversations from other profiles that don't expose those fields. 😊
